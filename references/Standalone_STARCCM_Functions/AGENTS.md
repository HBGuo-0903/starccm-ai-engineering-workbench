# Standalone STAR-CCM+ Functions

## Scope

本目录只保存“在 STAR-CCM+ 内部加载并执行”的 Java 宏、宏步骤和完整宏案例。目录的整理单位是一个可独立理解的功能或案例，而不是 GitHub 仓库、Java 文件或文件夹名称。

本目录不保存以下内容：

- 纯 Java 语法或只有一两个基础 API 调用的示例；
- 从命令行、Shell、Python、Batch、Slurm 或其他程序启动 STAR-CCM+ 的项目；
- 远程 `ServerConnection`、外部求解器、外部进程、集群提交、协同仿真等完整项目；
- 被多个案例共同依赖的公共 Java 库；
- 测试、临时尝试、重复版本和历史整理副本。

## Organization Rules

### Root-level layout

- 根目录下每一个子目录必须直接对应一个功能或完整案例。
- 不创建“几何分类”“后处理分类”等功能中间层，也不保留空的分类容器。
- 不按 GitHub 仓库划分；同一案例的多个 Java 文件必须放在同一个功能目录中。
- 目录名称使用能够表达用途的英文功能名，优先采用 `Action_Object_Condition` 或 `Object_Workflow` 格式。
- 禁止使用 `sources 1`、`sources 2`、仓库序号、无意义的 `Macro_` 或 `Demo_` 名称。

### Case boundary

- 多个 Java 文件如果共同完成一个连续工作流，视为同一个案例；必须按照实际执行顺序放在同一个 `Code` 目录中。
- 多个 Java 文件如果彼此没有调用关系、输入输出关系或执行顺序关系，则应拆成多个功能目录。
- 同一功能的历史版本只保留当前可用的最新版本。
- 旧版本、测试和临时尝试移入 `98_Previous_Organization`，不参与日常检索和运行。
- 如果一个宏只有基础语法/API 演示价值，没有独立工程功能，应移入同级 `Basic_Syntax`；这种内容不创建案例级 `README.md` 或 `AGENTS.md`。

## Directory Contract

每个保留的功能或案例目录必须能够回答“它解决什么问题、需要什么、如何执行、产生什么结果”。

```text
<Function_or_Case>/
├─ Code/
│  └─ 该功能或案例自己的 Java 文件
├─ Input_Files/       # 仅在确有输入文件时创建
├─ README.md          # 面向普通用户
└─ AGENTS.md          # 面向维护者
```

目录要求如下：

- `Code` 只保存该功能或案例自身的 Java 文件；
- 同一工作流的多个 Java 文件可以共存，但必须在文档和 Mermaid 中说明各文件的职责及执行关系；
- `Input_Files` 只用于真实运行所需的 `.sim`、`.csv`、CAD 文件、模板或其他输入文件；没有输入文件时不得创建空目录；
- `README.md` 说明普通用户关心的用途、前置条件、输入、运行方法、运行顺序和结果；
- `AGENTS.md` 说明维护者需要知道的功能边界、代码机制、输入输出、工作流和维护约束；
- 原始仓库来源应在 `README.md` 中注明，不能用仓库名称替代功能说明；
- 外部项目必须整体迁移到同级 `External_STARCCM_Runners`，不能把同一项目拆成一部分放在本目录、另一部分放在外部目录。

## Summary Contract

每个案例级 `AGENTS.md` 必须有一条面向功能和工程用途的 `Summary`，明确回答以下三个问题：

1. 通过什么方法或处理链工作；
2. 实现了什么具体功能；
3. 解决了什么工程问题或使用场景。

推荐句式：

`本宏通过 <具体方法或处理链> 实现 <具体功能>，解决 <明确的工程问题或使用场景>。`

Summary 必须描述宏对 STAR-CCM+ simulation 的实际作用，例如创建或修改模型对象、配置物理连续体、设置边界、执行网格、运行求解器、建立报告、更新场景或导出结果。

以下内容单独出现时不合格：

- “调用 API”；
- “执行宏”；
- “获取对象”；
- “更新状态”；
- 只列出 `execute()`、`getActiveSimulation()` 或 Java 类名；
- 只描述代码动作，没有说明功能用途和解决的问题。

## Workflow Contract

案例级 `AGENTS.md` 的 `Workflow` 部分必须只包含 Mermaid 代码块，不得在 Mermaid 之外写普通段落、编号步骤、项目符号或“输入 → 执行 → 输出”的文字流程。

Mermaid 必须根据对应 Java 文件实际重建，至少表达：

- 真实入口类和 `execute()` 方法；
- `Simulation`、Manager、对象树节点和已有对象的获取方式；
- 每个 Java 文件的职责及文件之间的执行顺序；
- 创建、查找、复用、修改和删除对象的先后关系；
- 代码中的条件分支、循环、已有对象检查、并行/串行关系和异常处理；
- 关键 STAR-CCM+ API、方法调用、属性设置及其对后续步骤的影响；
- 输入文件、simulation 中已有对象与代码固定名称之间的对应关系；
- 网格更新、求解运行、保存 simulation、导出结果等状态变化；
- 预期生成的对象、报告、场景、文件或求解状态，以及具体验证点。

Mermaid 节点应尽可能使用代码中的真实类名、方法名、管理器、对象名、属性名、文件名和条件。`调用关键 API`、`更新状态`、`检查输出` 等抽象节点不能代替实际执行逻辑；“输入 → 执行宏 → 输出”的三节点图也不合格。

涉及括号、冒号、斜线、逗号或中文长文本的 Mermaid 节点，必须使用带双引号的节点标签，例如 `A["ClassName.execute(): 获取 Simulation"]`。不得使用 `execute\(\)` 这种转义方式，也不得在未加引号的 `[...]` 或 `{...}` 标签中直接放置可能被 Mermaid 解析为图形语法的特殊字符。

根 `AGENTS.md` 不提供可直接复制的通用 Mermaid 模板。每个案例的图必须从实际源代码读取并单独编写；如果无法写出真实的执行链，应重新判断该内容是否只是 `Basic_Syntax` 示例，或是否需要补充代码分析后再归档。

## Boundary Rules

- 只使用 STAR-CCM+ 自身 solver、physics 或 coupling API，不会自动变成外部项目；判断依据是项目是否包含外部进程、远程连接、集群调度、外部求解器或完整外部启动流程。
- 只要项目包含上述外部运行边界，整个相关项目及其 Java、脚本、输入、配置和文档都放入 `External_STARCCM_Runners`，不得拆分。
- 跨多个案例复用的 Java 工具库放入同级 `Shared_STARCCM_Libraries`；本目录只保留案例自身的宏代码。
- 纯 Java 基础语法、集合、文件读写、异常、面向对象和简单 STAR-CCM+ API 示例放入 `Basic_Syntax`；这些文件直接放在该目录，不为每个小示例创建案例目录。

## Validation

整理或修改后，必须逐项检查：

- 根目录子目录都直接对应一个清晰功能或完整案例，没有分类中间层和空容器；
- 每个案例都有自己的 `Code`、`README.md` 和 `AGENTS.md`；
- `Code` 中的 Java 文件确实属于同一个功能边界，且不是重复版本、测试或无关文件；
- 同一案例的多个 Java 文件在 README 和 Mermaid 中体现了真实职责及执行顺序；
- `Summary` 同时说明方法、功能和解决的问题，而不是停留在 API 描述；
- `AGENTS.md` 至少包含 `Summary`、`Input`、`Output` 和 Mermaid-only 的 `Workflow`；
- Mermaid 使用实际代码中的类、方法、对象、条件和输出操作，不是通用三节点图或抽象节点拼接；
- Mermaid 语法中的特殊字符已正确处理，特别是括号、冒号、斜线、逗号和中文标签；
- 没有把外部项目拆分到本目录，也没有把共享库误当成案例代码；
- 没有空的 `Input_Files`，没有活动目录中的旧版本、测试文件和重复内容。
